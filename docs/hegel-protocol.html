Library goal & protocol reference

Hegel for Rust & the Hegel protocol

Hegel is a property-based testing library for Rust. It finds the inputs that break your code and shrinks them to the smallest failing example. This report documents what the library is for, and the exact protocol its frontend speaks to its native testing engine.

01 — Purpose

What Hegel is for

Most tests are example-based: you pick a handful of inputs and assert the output for each. Property-based testing inverts that. You state a property that should hold for every input, and the framework generates many inputs trying to prove you wrong. When it finds a counterexample, it shrinks it — repeatedly simplifying the input while the failure persists — until it hands you the smallest example that still breaks.

Hegel is a Rust implementation of that idea, based on Python's Hypothesis. You write a test with the #[hegel::test] attribute, draw values from generators, and assert your property. Hegel runs the body many times (100 by default) and minimizes any failure it finds. 

// A property: sorting should never change the length of a vector.
use hegel::generators as gs;
use hegel::TestCase;

#[hegel::test]
fn sort_preserves_length(tc: TestCase) {
    let xs = tc.draw(gs::vecs(gs::integers::<i32>()));
    let n = xs.len();
    let mut sorted = xs.clone();
    sorted.sort();
    assert_eq!(sorted.len(), n);
}

The canonical example in the project's README tests a hand-written my_sort that accidentally de-duplicates. Hegel doesn't just report a failing input — it reports the minimal one, [0, 0]: the smallest input that distinguishes "sort" from "sort and remove duplicates". That minimization is the feature that makes the failures actionable.

What the library gives you

  • Generators — primitives (integers, floats, text, booleans) and combinators (vecs, tuples, one_of, map/filter/flat_map), plus structured draws for dates, UUIDs, IP addresses, emails, URLs, and regex-matching strings.
  • Automatic shrinking — every failure is reduced to a minimal counterexample.
  • A reproduction database — failing examples are persisted under .hegel/ and replayed first on the next run, so a fixed bug stays fixed.
  • Stateful testing — model-based, rule-driven testing via #[hegel::state_machine] and variable pools.
  • Targeting — hill-climbing toward user-recorded scores to steer generation toward interesting inputs.

02 — Architecture

Architecture, and what the "server" really is

Hegel is split into a frontend and an engine. The frontend is the friendly Rust API you write tests against. The engine — a port of Hypothesis's conjecture core — owns the hard part: deciding what to generate, replaying the database, running the targeting search, and shrinking counterexamples.

On the word "server"

There is no network server and no separate process. The engine is compiled as a native library, libhegel, and linked into the same binary as your tests. Everything runs in-process. The "server" you talk to is that engine, and the "protocol" is the C ABI it exposes — the set of hegel_* functions below. Every language binding (Rust, and others) drives the exact same C ABI. So this document treats that C ABI as the protocol.

Calls fan down through the frontend and cross the C ABI once; every language binding links the same libhegel engine.

There is no background thread. A run handle is a suspended engine — a future the client resumes on its own thread every time it asks for the next test case. All generation, mutation, and shrinking happen inside those calls.

Where the name "libhegel" comes from

libhegel is not a separate project — it is the engine crate (hegel-c, package hegeltest-c) compiled as a C library. The crate declares crate-type = ["cdylib", "staticlib", "rlib"], so Cargo emits a native shared and static library; by the usual Unix convention the file gains a lib prefix. The Cargo lib is technically named hegel_c — so it can coexist with the frontend's hegel lib in one dependency graph — which produces libhegel_c.{so,a} locally. But the header, the exported hegel_* symbols, and the release binaries are all branded libhegel: every GitHub release ships a libhegel-<os>-<arch> artifact for other language bindings to link against. In short, "libhegel" is the distributable native form of the engine.

Why a C ABI at all?

The Rust frontend does not strictly need C: the engine is an ordinary Rust crate compiled into the same binary, and it even exposes a native Rust entry point (run_native_async in hegel-c/src/embed.rs). The C ABI exists because Hegel is a universal property-based testing framework — one engine meant to back frontends in many languages — and C is the common denominator of foreign-function interfaces.

  • Universal interop. Almost every language can call C — Go via cgo, Java via JNI/Panama, Python via ctypes/cffi, Ruby via FFI, Node via N-API — but none can call another language's native ABI. A C ABI lets all of them drive the identical engine.
  • A stable contract. Rust has no stable ABI; its calling convention and struct layout can shift between compiler versions, so Rust functions can't be exposed reliably across a precompiled boundary. repr(C) + extern "C" pin a fixed contract — what makes the shipped libhegel-<os>-<arch> binaries linkable from any toolchain.
  • One engine, identical behavior. The generation and shrinking logic is subtle; reimplementing it per language would drift. A single native library keeps every binding's results identical and leaves one engine to maintain.
  • Designed for foreign callers. The protocol's shape reflects this: the explicit HegelContext error channel — instead of thread-local state — exists precisely because runtimes like Go migrate tasks between OS threads and languages like Java free handles from finalizer threads.
  • Rust dogfoods the same path. Rather than bypass C through the native entry point, the frontend drives the very same hegel_* ABI every other binding uses — so the boundary is exercised continuously and Rust behaves exactly like every other language.

The build pipeline

A natural question: is Rust the source of truth, and is it "compiled to C"? The first half is yes; the second is a common misconception. Nothing is transpiled to C. The Rust source is the single source of truth, and the compiler emits a native library that merely speaks the C ABI — a stable calling convention — directly. The only C artifact that is generated is the header.

One Rust source, two outputs: cargo compiles the engine to a native C-ABI library; cbindgen (run from build.rs) regenerates the header.

  • Source of truth — hegel-c/src/lib.rs holds the #[no_mangle] extern "C" hegel_* functions.
  • The library — cargo build -p hegeltest-c compiles that Rust straight to machine code as a cdylib + staticlib. rustc/LLVM emits the binary directly; there is no intermediate C source and no C compiler in the loop.
  • The header — hegel.h is the one generated C artifact: cbindgen reads the Rust source (driven by hegel-c/build.rs, configured by cbindgen.toml) and writes the declarations. It is checked into the repo and refreshed with just c-header.
  • Drift guard — a normal build compares the freshly generated header against the checked-in one and panics if they differ, so the header can never fall out of sync with the Rust it describes.

03 — Calling convention

Protocol conventions

Every function in the protocol follows the same shape, so the rules below hold everywhere.

The universal call shape

  • Every function takes a hegel_context_t *ctx as its first argument and returns a hegel_result_t code. The two exceptions are hegel_context_new (returns the context) and hegel_context_last_error (returns the message pointer).
  • Anything else a call produces — a handle, a string, a count, a drawn value — is written through a trailing out-parameter named out_*.
  • HEGEL_OK is 0; every error is negative, so result < 0 tests for failure.
  • A NULL context is allowed and simply opts out of error messages — the call still returns its code.

The context is the error channel

Diagnostics are recorded on the caller-supplied hegel_context_t, not in thread-local state. This is deliberate: runtimes that migrate a task between OS threads mid-call (Go's goroutines, for example) would otherwise write an error on one thread and read it on another. You create one context per test (or per thread), pass it everywhere, and read the last message with hegel_context_last_error(). A context must not be shared across threads concurrently.

Pointer ownership

Pointers you pass into a function are always yours — the library copies whatever it needs to keep, so you may free or reuse them as soon as the call returns. Of the pointers handed back, a specific set are owned by you and must be released with a matching free; every other returned string is borrowed and valid only until a documented point.

Threading & the test-case family

A single test-case handle must be driven by at most one thread at a time; concurrent use of one handle surfaces as HEGEL_E_CONCURRENT_USE. To generate from several threads, hegel_test_case_clone the handle — a clone draws from an independent choice stream but shares the underlying case's outcome and budgets. A handle and all its clones form a family; the shared case is released only when the last handle is freed. Completion is first-caller-wins and family-wide: the first hegel_mark_complete anywhere in the family records the outcome, and later calls on other handles are safe no-ops.

04 — Sequence

The run lifecycle

A full property-test run (mode HEGEL_MODE_TEST_RUN) walks these steps.

Every arrow runs on the client's own thread — the engine has no thread of its own; it is resumed inside each call.

  1. Create a context

    hegel_context_new() — the per-thread error channel passed to every later call.

  2. Build & configure settings

    hegel_settings_new, then any hegel_settings_set_* setters (test-case count, phases, seed, database, verbosity…).

  3. Start the run

    hegel_run_start snapshots the settings and returns a run handle. No test case exists yet; an optional callback redirects the engine's per-line output.

  4. Pull the next test case

    hegel_next_test_case resumes the engine on your thread until it offers a case — or writes NULL to signal the run is finished.

  5. Drive the case

    Call the hegel_generate_* draws, open/close spans, use collections, pools, state machines, and record hegel_target scores. Clone the handle for concurrent draws.

  6. Complete & free the case

    hegel_mark_complete with VALID, INVALID, OVERRUN, or INTERESTING; then hegel_test_case_free. Loop back to step 4.

  7. Read the aggregate result

    Once the loop ends, hegel_run_result gives a snapshot: hegel_run_result_status plus each failure's origin and reproduction blob (or a run-level error message).

  8. Final replay (optional)

    hegel_test_case_from_blob rebuilds the minimal counterexample from its base64 blob so the client can regenerate the diagnostic and re-raise its own failure.

  9. Tear down

    Free the result, run, settings, and context. Result and failure snapshots are independent and may outlive the run.

Result & status codes

hegel_result_t — per-call return code

VariantValueMeaning
HEGEL_OK0Success.
HEGEL_E_STOP_TEST-1Choice budget exhausted for this case; abort the body. Treat like a validly-completed case.
HEGEL_E_ASSUME-2An assume/reject precondition failed; discard the case as invalid.
HEGEL_E_BACKEND-3The engine reported an error; read hegel_context_last_error().
HEGEL_E_INVALID_HANDLE-4A required handle pointer was NULL.
HEGEL_E_INVALID_ARG-5A non-handle argument was invalid — NULL, inverted bounds, non-UTF-8, etc.
HEGEL_E_ALREADY_COMPLETE-6A primitive or mark_complete was called on an already-completed handle.
HEGEL_E_NOT_COMPLETE-7Read before ready — next case requested before completing the previous, or result read before the run finished.
HEGEL_E_INTERNAL-8An internal invariant failed inside libhegel (file a bug).
HEGEL_E_CONCURRENT_USE-9One handle used from two threads at once; clone the handle for concurrency.

hegel_status_t — outcome of one test case

Passed to hegel_mark_complete to conclude a case.

StatusValueMeaning
VALID0The body ran to completion and the property held.
INVALID1A precondition rejected the draw; discard without counting against the budget.
OVERRUN2Ran out of choice budget mid-case (a draw returned STOP_TEST); inconclusive.
INTERESTING3The property failed; a candidate counterexample. Pass a stable origin so the shrinker can group the bug.
Origin strings are load-bearing

For an INTERESTING case, origin identifies which bug this is. Identical origins are grouped and shrunk together; distinct origins partition the shrink budget. Derive it from the failing assertion's location (the convention is "Panic at <file>:<line>"), never from a message that depends on the drawn values — otherwise every distinct draw looks like a fresh bug and the shrinker never converges.

hegel_run_status_t — aggregate run outcome

StatusValueMeaning
PASSED0The property held across every generated case.
FAILED1The property failed; inspect counterexamples via the failure getters.
ERROR2The run itself failed — a health check, nondeterminism, an engine panic — and produced no verdict.

08 — Rust binding

The Rust safe layer

The frontend never touches the raw hegel_* functions directly. A single module, src/ffi.rs, is the only unsafe boundary; it wraps the protocol into safe, drop-freeing Rust types that the rest of the library uses. The context lives in a thread_local! so every fallible call and its error read happen on the same thread.

Safe typeWrapsRole
